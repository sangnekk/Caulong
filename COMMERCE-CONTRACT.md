# Commerce implementation contract

Laravel 13 answering Inertia page props; pages are React views in the Next.js app (frontend/); use existing dependencies, integer VND. UI Vietnamese, plain wording. No fabricated inventory/prices for real brands. Seed demo products explicitly is_demo=true (fictional names, existing generic poster) and label demo orders. Public / remains landing; /products is store. No payments/AI claimed live without configured provider.

## Catalog schema

products: id, brand_id nullable FK nullOnDelete, category_id nullable FK nullOnDelete, name(160), slug unique(180), description text, image_path nullable string (relative public disk path or /models/hyper-core-poster.png), specs JSON nullable, play_style(attack|speed|balanced), skill_level(beginner|intermediate|advanced|all), is_active boolean default false, is_featured boolean false, is_demo boolean false, timestamps.

product_images: id, product_id FK cascadeOnDelete, path (public disk), hash char(64) sha256 of the file, position, timestamps. Further photos only; the main photo stays products.image_path. At most 12 per product.
Product relations brand/category/variants. Price/stock stored ONLY variants. Product image_url accessor: safe local Storage public URL, static poster fallback. Specs fields weight, balance, stiffness, material, max_tension strings (not unverified medical claims). Product catalog scopes active and variants active. Order item restrict deletion purchased variant; deactivate instead.

## Orders schema

orders: id, public_id unique UUID, checkout_token unique UUID, user_id nullable FK nullOnDelete, name,phone,address,email nullable,notes nullable,status string default pending,payment_method string cod,payment_status string unpaid,subtotal/shipping_fee/total unsignedBigInteger,is_demo boolean false, timestamps.
order_items: id,order_id cascade,variant_id nullable FK restrictOnDelete,product_name,variant_name,sku,unit_price unsignedBigInteger,quantity unsignedInteger,line_total unsignedBigInteger,timestamps.
Order relationships items,user. No payment provider secrets or fake callback. COD marked paid only via explicit admin confirmation money collected, not merely delivered.
OrderService admin transitions uses transaction/lock: pending->confirmed|cancelled; confirmed->shipped|cancelled; shipped->delivered; delivered terminal. Cancel restocks exactly once, sorted variant lock; do not restore orders already cancelled. Admin calls OrderService.transition(Order,string) and markCodPaid(Order); worker implement.
payment_method is cod | bank_transfer; payment_status is unpaid | paid | refunded. A bank_transfer order that is unpaid cannot be moved to confirmed by transition (error status): PaymentService::settle confirms it. An order whose payment_status is paid cannot be cancelled by transition (error status): PaymentService::refund cancels it. Cancelling an order sets its pending payments to cancelled. markCodPaid refuses anything but a delivered cod order.

## Bank transfer

payments: id, order_id FK cascadeOnDelete, method(30) (bank_transfer), amount unsignedBigInteger (the order's total), reference(40) unique ("DH" + the order's 8-character code; two more characters if that is taken), status pending|paid|expired|cancelled|refunded (default pending), provider_transaction_id(100) nullable unique, expires_at, paid_at, confirmed_by nullable FK users nullOnDelete, refunded_at, refunded_by nullable FK users nullOnDelete, payload JSON nullable, timestamps; index (status, expires_at). One row per bank_transfer order, made in the checkout transaction; none for cod. Order::payment() is the latest.
Settings (ShopSettings::bankTransfer): bank_transfer_enabled (default config shop.bank_transfer.enabled = false), bank_transfer_hold_hours (1..168, default 24), bank_bin (a key of config shop.banks: NAPAS codes of banks that take a VietQR transfer), bank_account_number ([0-9A-Za-z]{4,19}), bank_account_name (<=60, saved in capitals). ready = enabled, a known bank, a number and a name. PUT /admin/settings takes them (a request without them leaves them unchanged); enabled is refused without the other three. GET /admin/settings also returns banks:[{bin,name}] and bankQr (the saved account as a QR image without an amount, or null).
PaymentService::methods(cart): bank_transfer is offered when ready, the cart holds no demo product and its total is above 0. OrderService::checkout checks the same again inside its transaction (error payment_method) and sets expires_at = now + hold hours.
PaymentService::summary(order) -> null | {status, reference, amount, expires_at, paid_at, account: {bank, number, name, qr} | null}. account is given only while status is pending, from the account saved now; qr is "data:image/svg+xml;base64,…" of the VietQR text (App\Support\VietQr::payload: EMV fields, NAPAS GUID A000000727, service QRIBFTTA, amount, the reference as purpose, CRC-16/CCITT-FALSE). The payment's id, provider_transaction_id and payload never leave the admin.
settle(payment, by?, amount?, transaction?, payload?): order row locked, then the payment. Already paid: returns it, nothing more. Else it must be pending and its order pending (error payment), and a given amount must equal payment.amount (error payment). Sets paid, paid_at, confirmed_by, provider_transaction_id, payload; order payment_status paid, paid_at now, status confirmed. The call that settled it sends the order_paid email. No provider calls it yet: staff do.
refund(payment, by): must be paid and its order pending or confirmed (error payment). Sets refunded, refunded_at, refunded_by; order payment_status refunded, paid_at null (so it leaves every "collected" figure); then the order is cancelled (stock back, coupon use released, order_cancelled email, which says the money was sent back). Already refunded: nothing more.
expireOverdue() (`php artisan orders:cancel-unpaid`, every 15 minutes): each pending payment past expires_at becomes expired and its pending, unpaid order is cancelled; that order's order_cancelled email says the transfer was not received in time. It cannot see the bank: an order paid but not yet settled is cancelled too. settle on an expired or cancelled payment is refused.
POST /admin/orders/{order}/payments/{payment}/confirm admin.orders.payments.confirm -> settle by the signed-in member of staff; POST …/refund admin.orders.payments.refund -> refund. Both carry can:manage-shop and scoped bindings: a payment of another order is 404.
GET /admin/orders ?payment=paid|unpaid|transfer (transfer = bank_transfer, unpaid, pending); q also matches a payment's reference exactly (any case). GET /admin/orders/{order} also returns payment: {id,status,reference,amount,expires_at,paid_at,refunded_at,confirmed_by (name),refunded_by (name)} | null. The CSV export's last column is "Cách thanh toán"; "Thanh toán" reads Đã thu, Đã hoàn tiền or Chưa thu. GET /admin returns todo.awaiting_transfer, and todo.pending_orders no longer counts those orders.
GET /account orders[] also carry payment_method.

## Email

users.marketing_opt_in_at nullable timestamp: when the customer agreed to promotional email; null = not agreed or taken back. Never ticked for them.
email_logs: id, type(40), recipient(190), subject, status queued|sent|failed (default queued), provider_message_id nullable, error nullable text, user_id nullable FK cascadeOnDelete, order_id nullable FK nullOnDelete, sent_at nullable, timestamps. Rows older than 365 days are pruned daily; nothing that must outlive a year relies on them (an offer is remembered by its coupon).
Every email goes through EmailService::send(type, recipient, ShopMail, user?, order?): log row first, then the App\Jobs\SendEmail job (3 tries, 60 s then 600 s apart; failed with the reason after the last). Nothing is sent inside a request, and a failure never fails the order or the sign-up. Laravel's verify-address and reset-password notifications are queued with the same tries and logged once sent.
Types: transactional welcome|order_placed|order_paid|order_shipped|order_delivered|order_cancelled|coupon (and service_placed|service_ready|service_cancelled) go to any usable address; marketing abandoned_cart|winback|post_purchase|vip only to a non-admin customer with marketing_opt_in_at set and a verified address, checked when queued and again when the worker sends (a customer who stopped in between gets nothing; the row ends failed with that reason). No email for a demo order or to an address at khach-mau.invalid. Marketing emails carry the unsubscribe link in the body and in List-Unsubscribe; transactional ones never do.
A customer's coupon is emailed as marketing (type = its campaign) when coupons.campaign is winback or vip, whoever sends it; any other personal coupon is a transactional gift (type coupon).
Order emails are sent once per step, by the call that moved the order: placed at checkout (not on a replayed token), paid when a bank transfer is settled, then shipped, delivered, cancelled. Confirming a cod order sends nothing. The placed email of a bank_transfer order carries the account, the amount, the reference and the deadline (no QR image).
MarketingAutomation (php artisan marketing:run {automation?}; scheduled in routes/console.php in config shop.timezone, after crm:segment): each automation is off until its marketing_<name> setting is on; real orders and non-demo customers only; at most config shop.marketing.batch (200) emails per automation per run. abandoned_cart: last add_to_cart at least marketing_abandoned_cart_hours ago (1..72) and within 7 days, no order since, at most one per customer per 7 days. winback: segment inactive with a real order, own coupon (percent, max_discount 300000, single use), at most one per 180 days. post_purchase: marketing_post_purchase_days after delivered_at (up to 14 days late), once per order. vip: segment vip, own coupon, once per customer for good. An offer already made is known by its coupon (campaign + user_id), so a failed or dropped email never makes a second coupon.
MAIL_MAILER=resend: App\Mail\ResendTransport posts to https://api.resend.com/emails with Laravel's HTTP client (no SDK), key from RESEND_API_KEY only, 15 s timeout; Resend's id is kept in email_logs.provider_message_id. Tests fake the HTTP call; no real delivery is claimed.

## Support chat

support_conversations: id, session_key(64) (the visit: CustomerEvents::sessionKey, an HMAC of a random value kept in the session), user_id nullable FK cascadeOnDelete (the customer's account; never a staff account), status open|pending|resolved|closed (default open), needs_human boolean (a ticket for staff; false while only the assistant answered), assigned_to nullable FK users nullOnDelete, last_message_at, resolved_at, closed_at, access_code_hash(64) nullable unique, access_code_expires_at, timestamps. support_messages: id, conversation_id FK cascadeOnDelete, sender customer|bot|admin, body, action_url nullable, action_label nullable, read_at nullable, timestamps.
All rules are in App\Services\SupportChat. A customer message sets status open (and, in a ticket, is unread for staff); a staff reply sets pending; resolve sets resolved (+resolved_at); close sets closed (+closed_at); a message to a closed conversation starts a new one; `php artisan support:close-resolved` (daily) closes what has been resolved for config shop.support.resolved_days (3).
Whose conversation a request is in: the one whose id the session holds, unless it belongs to an account other than the signed-in customer's (then none); else, for a signed-in customer, their latest conversation that is not closed. Signing in gives the visit's guest conversation to the account (Login event), never to a staff account.
The widget's endpoints are JSON and are Laravel paths (next.config.ts rewrites /support-chat/\*):
GET /support-chat/messages -> {status|null, messages:[{id,sender,body,action_url,action_label,created_at}] (latest 100, oldest first), can_request_code:boolean (status resolved or closed), code_expires_at|null}. POST /support-chat/messages {message<=1000} -> the same; 8 messages a minute per visit.
POST /support-chat/code -> {code:"ABCDE-FGH23", expires_at} for the visitor's own resolved or closed conversation, else 422. Ten characters from an alphabet without look-alikes; only hash_hmac('sha256', code, app.key) is stored; a new code replaces the old; good for config shop.support.code_days (30).
POST /support-chat/lookup {code} -> {status, started_at, closed_at|null, messages (latest 200)}; case, spaces and dashes in the code do not matter. Unknown and expired codes get the same 404 {message}; after 5 wrong codes from one address, 429 for 10 minutes. A right code uses up no attempt.
GET /support-chat/conversations/{id} (auth) -> the same transcript for the customer who owns it, 404 for anyone else. GET /account returns conversations:[{id,status,started_at,last_message_at,excerpt,messages}] (latest 20).
GET /support-chat/context -> {purchased_products:[name]} for the widget's shortcuts.
Rate limits: every route limit names its own counter (throttle:N,M,name). An unnamed limit shares one counter per visitor across all routes, which the widget's polling (every 4 s) would exhaust for sending messages, coupons and checkout.

## Stringing service

service_strings: id, name(120) unique, brand(80) nullable, gauge(20) nullable, price unsignedBigInteger (dong for the string of one racket), is_active boolean true, timestamps. A material of the service, not a product: no stock, never in the cart. Switched off, never deleted.
service_orders: id, public_id unique UUID, booking_token unique UUID, user_id nullable FK nullOnDelete (a customer's account; never a staff account), name(120), phone(20) indexed, email(190) nullable, service_type shop_string|own_string, racket(160), service_string_id nullable FK nullOnDelete, string_name(160) nullable (the string's label as it was when requested, or what the customer says they bring), tension_kg decimal(4,1), quantity unsignedTinyInteger, notes nullable, preferred_at nullable (UTC), status pending|confirmed|in_progress|ready|completed|cancelled (default pending, indexed), technician_id nullable FK users nullOnDelete, string_price and labor_fee (per racket, as quoted when requested), total, confirmed_at/in_progress_at/ready_at/completed_at/cancelled_at, timestamps.
All rules are in App\Services\StringingService. Transitions under a row lock: pending->confirmed|cancelled; confirmed->in_progress|cancelled; in_progress->ready|cancelled; ready->completed; completed and cancelled are terminal. Asking for the status a request already has changes nothing and sends nothing. total = quantity × (string_price + labor_fee), worked out by the server from the string's price and the stringing_fee setting; own_string charges the fee alone. The browser sends choices, never a figure.
GET /services services.index -> shop/services {service:{enabled, fee, tension:{min,max}, max_rackets, strings:[{id,label,price}] (active only, cheapest first)}, bookingToken UUID}. The token is made for each page and kept nowhere: a first-time visitor's browser has no session cookie yet when the page is built, so nothing could be kept for them in the session.
POST /service-orders service-orders.store (throttle 6/min, guests too) {booking_token uuid, name<=120, phone Vietnamese format as checkout, email nullable<=190, service_type, racket<=160, service_string_id (required for shop_string, an active string), string_name nullable<=120 (own_string only), tension_kg between config shop.stringing.tension_min and tension_max (8..15) in steps of 0.5, quantity 1..max_rackets (10), preferred_at nullable "Y-m-d\TH:i" in config shop.timezone, in the future and within book_ahead_days (30), notes nullable<=1000} -> redirect to the request's page. A token already used returns the same request to the session that made it (no second row, no second email) and is refused to any other session (error booking_token). Refused while stringing_enabled is off (error booking_token). A signed-in customer's request gets their user_id; one made while signed in as staff gets none.
GET /service-orders/{serviceOrder:public_id} service-orders.show -> shop/service-order {order:{id,public_id,code (first 8 characters of public_id, upper case),status,racket,string_name,service_type,tension_kg,quantity,total,created_at,name,phone,email,notes,string_price,labor_fee,preferred_at}, justPlaced:boolean, address}; only the session that made it (session key service_order_access, latest 25), the owning account, or a valid relative signature (App\Support\Frontend::serviceOrder, 60 days, the link in its emails); 404 otherwise. booking_token is never serialized.
Emails (EmailService::service, transactional): service_placed when the request is made, service_ready and service_cancelled by the call that moved it; to the request's email, else the account's; none when neither exists. The other steps send nothing.
GET /account also returns serviceOrders:[summary] (latest 10); GET /admin/customers/{user}?tab=services returns services:[summary] (latest 50); the chat context returns services:[summary] (latest 3). summary = {id,public_id,code,status,racket,string_name,service_type,tension_kg,quantity,total,created_at}.
GET /admin/service-orders admin.service-orders.index ?status=(a status)&q=(number, "#number", start of public_id, name or phone) -> admin/service-orders {orders (pagination 20: id,public_id,code,name,phone,service_type,racket,string_name,tension_kg,quantity,total,status,preferred_at,created_at,technician_name), filters, counts:{all, one per status}}. GET /admin/service-orders/{serviceOrder} -> admin/service-order {order (row + email,notes,string_price,labor_fee,technician_id,customer:{id,name,email}|null,steps:{confirmed,in_progress,ready,completed,cancelled}), staff:[{id,name}] (every staff account), related (latest 5 from the same phone)}.
PATCH /admin/service-orders/{serviceOrder} takes one change at a time: {status} (the next step), {technician_id} (a staff account or null) or {total} (0..100000000). technician_id and total are refused once the request is completed or cancelled (error status).
GET /admin/service-strings admin.service-strings.index -> admin/service-strings {strings:[{id,name,brand,gauge,price,is_active,label,requests}]} (active first). POST /admin/service-strings, PUT /admin/service-strings/{serviceString} {name (unique), brand, gauge, price 0..100000000, is_active}. No delete.
PUT /admin/settings also takes stringing_enabled (boolean) and stringing_fee (0..5000000); a request without them leaves them unchanged. Defaults in config shop.stringing (enabled true, fee 0).

## Staff roles

users.is_admin marks a staff account (never a customer: no segment, no events, no marketing). users.role says what it may do: admin | support; a staff account without a role is an admin (User::staffRole()). Gate manage-shop = role admin. Every /admin route but the dashboard redirect and admin.support-chat.\* carries can:manage-shop (a test checks each route). Support staff: GET /admin redirects to /admin/support-chat; signing in lands there; any other admin page is 403. Shared prop shop.staff_role: 'admin'|'support'|null; pending_orders and pending_reviews are 0 for support staff. `php artisan shop:make-admin {email} {--role=admin|support}`. No staff management screen yet.
